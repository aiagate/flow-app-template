# 業務に応じた実装の選び方

このテンプレートの目的は、設計の一貫性を保ち、業務ロジックに集中することです。
すべての機能に集約・Value Object・GenericRepositoryを要求することではありません。
入口はApplicationの契約を呼び、Infrastructureが外部I/Oを引き受ける依存方向を保ちながら、必要な実装を選びます。

## 事業上の位置付けと実装の複雑さを分ける

DDDのコア・支援・汎用はサブドメインの事業上の位置付けです。コアは競争上の差別化を担う領域、支援は事業に必要な固有機能、汎用は既存製品等の利用を検討できる領域です。このテンプレートだけでは、どの業務がコアかを決定できません。

実装方法は、これとは別に不変条件・状態遷移・競合・トランザクション境界の複雑さで選びます。コアでも単純な処理はあり、支援領域でも複雑な承認規則があります。分類ごとに継承階層や共通の基底クラスは作りません。

| 実際に守る性質 | 最初に検討する実装 | このリポジトリの例 |
| --- | --- | --- |
| 単純な入力検証と独立した書き込み | Transaction Scriptと用途専用のPort。独立した集約・VO・マッパーは必要性が出てから追加 | [軽い機能の実装例](../../examples/simple_feature/README.md) |
| 状態遷移と複数の業務規則 | 振る舞いを持つドメインモデルとUoW。必要な取得・保存を専用Portまたは既存Repositoryに委ねる | `TeamMembership.approve()` / `leave()` とmembership usecases |
| 表示・検索・履歴の読み取り | 必要なDTOを返すQuery Port。書き込み集約の完全復元を強制しない | `IChatHistoryQuery` / `SQLAlchemyChatHistoryQuery` |
| 外部製品で充足できる機能 | 導入費用と運用・変更費用を比較し、必要な接点だけPortで表す | 入口SDKは必要なものだけ導入する |

Transaction Scriptでも、入力検証、認可、制約、原子性、失敗時の扱いは必要です。省略するのは不要なモデル変換や登録であり、正しさの条件ではありません。ドメインモデルを使う場合も、単純な値まで機械的にVOにせず、意味のある検証・同一性・操作を持つかで判断します。

## Repositoryを選ぶ

既存の`GenericRepository`は、明示的マッピングを使った集約スナップショット保存、Version、監査日時、追記専用という契約を共有できる場合の選択肢です。新機能がこれらの意味に合うなら利用できます。形だけを合わせるために不要なVersionや監査フィールドを足しません。

次の場合は用途専用のPortを優先して検討します。

- 取得条件や保存の意味を業務語彙で示したい。
- 集約全体の読み書きではなく、一つの更新や検索を行いたい。
- 汎用保存のVersion・監査・スナップショット契約が適合しない。

既存UoWの同じトランザクションへ参加する専用実装は、Composition Rootで`SQLAlchemyUnitOfWork(..., repository_factories=...)`を構築し、`GetCustomRepository()`で取得します。標準`DatabaseModule`は空のfactory構成なので、アプリへの採用時にはproviderを変更します。[実行例のComposition Root](../../examples/simple_feature/composition.py)がその配線を示します。実装にはUoWのSessionを渡します。Repository内部で別Sessionを作ったり成功をcommitしたりしません。独立した単一操作なら、専用Portの契約がトランザクション全体を所有する方式も選べます。両者の寿命やcommit責任を混在させません。

SQLAlchemyのSessionを使うこと自体は特殊ではありません。ただし、このテンプレートでユースケースへ直接Sessionを露出する方式は、既存の依存境界を変える選択です。『薄いから』だけで標準へ追加せず、対象アプリが境界の費用と便益を判断します。

Repositoryは保存・取得の意味を明示するための境界です。共通化の便益は[FowlerのRepository](https://martinfowler.com/eaaCatalog/repository.html)も参照してください。

## 複雑さを増やす契機

単純な処理に状態遷移や複数箇所から共有する不変条件が増えたら、その規則をドメインへ移します。複数の書き込みを一緒に確定する必要が生じたら、専用Port内部のトランザクションから共有UoWへ境界を見直します。利用者や変更理由の違いを無視して、同じデータ形だから統合することは避けます。

入口の追加は業務モデルの複雑化と別問題です。この実装例では入口SDKの依存構成を変更しません。アプリで不要な入口を保守対象から外す場合は、その入口のコード・依存・CIの扱いも別途判断します。

## 検証方法を選ぶ

実装方式を選んだあと、業務上の約束をどう検査するかも性質で選びます。例ベースの
テストで足りる処理にPBTや形式モデルを要求しません。状態遷移、入力の組合せ、操作順、
複数行にまたがる整合性が関わる場合の手法の目安と、Membershipを例にした実行方法・
保証範囲は [業務ルールを検証へつなぐ手順](./VERIFICATION.md) を参照してください。

## イベント処理の境界

標準DIは`InMemoryEventBus`であり、プロセス間を配送しません。APIのlifespanはイベントバスの起動・購読登録を行わず、別プロセスのWorkerにもそのキューは届きません。`user.created`の発行成功は後続処理の実行保証ではありません。

この実装例と依存分離は、イベント配送を変更しません。後続処理を必要とするアプリは、同一プロセスでの起動・購読・停止を配線するか、プロセス間配送を選択する必要があります。必達が必要ならDB更新との原子性を含めてOutbox等を要件化します。単に外部Brokerや汎用抽象を追加して解決済みとはしません。
